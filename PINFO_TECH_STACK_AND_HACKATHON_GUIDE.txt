PART 3: COMPLETE TECH STACK BREAKDOWN (THE EXACT TOOLS WE USE)
--------------------------------------------------------------------------------

[1] FRONTEND (User Interface & Client Layer)
--------------------------------------------------------------------------------
- Framework: Next.js 16 (App Router) with React 19.
  * Why: Server-side rendering (SSR), fast client navigation, SEO optimization,
    and instantaneous static page delivery.
- Language: TypeScript (Strict Type Safety).
  * Why: Catches bugs at compile time instead of in production during the demo.
- Styling: TailwindCSS (Modern Dark-Mode Design System).
  * Aesthetics: Emerald and deep slate glassmorphism palette, responsive mobile-first
    cards, fluid micro-interactions, custom typography.
- Icons: Lucide React (featherweight SVG vector icons).
- Notifications & Feedback: Sonner (buttery-smooth toast notification toasts).
- Barcode Scanner Engine:
  * Native Web Shape Detection API (BarcodeDetector) with WebAssembly / HTML5
    Canvas fallback.
  * Real-time 60 FPS live camera barcode detection across EAN-13, UPC-A, Code-128,
    and QR codes without downloading native mobile apps.
- Label OCR / Image Ingestion:
  * HTML5 Canvas image preprocessing with client-side downsampling and EXIF
    rotation before transmission to backend AI.
- Automated Testing Suite: Vitest + React Testing Library (139 automated tests
  passed with zero failures).
- Hosting: Vercel Global Edge Network (sub-millisecond static asset delivery,
  automated SSL certificate, auto-deploying CI/CD pipeline).


[2] BACKEND (API & Microservices Layer)
--------------------------------------------------------------------------------
- Framework: FastAPI (Python 3.11 / Python 3.14 compatible).
  * Why: One of the fastest Python frameworks in existence, built on Starlette
    and Pydantic. Fully asynchronous (async/await), supporting high concurrent
    traffic with low memory usage.
- Server Runtime: Uvicorn (ASGI lightning-fast HTTP server).
- Data Validation: Pydantic v2 (Pydantic-Settings, EmailStr).
  * Enforces strict schema validation for every incoming request and outgoing response.
- HTTP Client: HTTPX (Async HTTP client with connection pooling and timeouts).
  * Used for non-blocking parallel queries to external APIs.
- Hosting: Render Web Service (containerized Linux execution, auto-scaling, CI/CD).


[3] PERSISTENCE & DATABASE ARCHITECTURE (ZERO DATA LOSS DUAL-ENGINE)
--------------------------------------------------------------------------------
*Judges LOVE this engineering design because it solves cloud container resets.*

- Primary Cloud Engine: Cloud PostgreSQL (psycopg2-binary driver).
  * Provisioned via Render Blueprint (render.yaml), Neon.tech, or Supabase.
  * Hosted externally in the cloud: immune to container restarts, sleep periods,
    or deployments.
  * Stores user credentials, profiles, sessions, scans, and audit trails permanently.

- Local / Offline Engine: SQLite 3 with WAL Mode (Write-Ahead Logging).
  * High-concurrency local database providing zero-latency reads and writes.

- Architectural Innovation: Connection & Cursor Wrappers.
  * We built custom Python wrappers (PostgresConnectionWrapper and PostgresCursorWrapper)
    that dynamically translate SQLite-style `?` queries to PostgreSQL `%s` parameters,
    allowing 100% identical application code to run seamlessly on both engines.

- Disaster Auto-Recovery & Snapshots:
  * Whenever a user registers, logs in, or scans a product, the backend automatically
    flushes an atomic snapshot to `pinfo_snapshot.json`.
  * If the server ever reboots into a fresh environment, `auto_restore_if_needed()`
    detects missing accounts and automatically re-populates the database without
    overwriting existing records.

PART 5: HOW TO ANSWER TOUGH JUDGE QUESTIONS (CHEATSHEET)
--------------------------------------------------------------------------------

Q1: "What happens if the product barcode is not in the database?"
YOUR ANSWER:
"Great question! We built a dual-fallback system. If a barcode isn't in Open Food
Facts, the user simply clicks 'Scan Label' and snaps a photo of the ingredient
list. Our Google Gemini 2.5 Flash OCR analyzes the packaging image directly and
constructs the nutrition profile on the fly."

Q2: "How do you protect user passwords and credentials?"
YOUR ANSWER:
"All passwords are encrypted using industry-standard salted bcrypt before storage.
API communications are secured via HTTPS with Bearer JWT tokens. Additionally,
the Admin panel is protected by role-based access control (RBAC), and our backend
features rate-limiting and payload size security middleware."

Q3: "How do you scale this if 100,000 users join tomorrow?"
YOUR ANSWER:
"The architecture is designed for cloud-native horizontal scalability:
1. The frontend runs on Vercel's Edge CDN, which scales across global points of
   presence automatically.
2. The FastAPI backend is stateless and can scale to multiple container instances
   behind a load balancer.
3. The database connects to managed Cloud PostgreSQL (e.g., Render, Neon, or
   Supabase) with connection pooling."

Q4: "Why did you choose Google Gemini over OpenAI GPT-4?"
YOUR ANSWER:
"We chose Google Gemini 2.5 Flash because of its multimodal vision capabilities,
lower token latency (essential for real-time camera scanning), and native JSON
structured output via the official Google GenAI Python SDK."

Q5: "How does the dual-engine database work?"
YOUR ANSWER:
"We developed custom connection and cursor wrappers in Python that abstract the SQL
dialect. Whether querying Cloud PostgreSQL with `%s` or local SQLite with `?`, the
application runs identical code. Plus, on every update, atomic snapshots are saved
so that if a container restarts, missing records are automatically restored."
